Cliente Python (strategodata_client)

Para consumo desde Python, strategodata_client es más eficiente que pasar por HTTP/JSON: lee/escribe parquet directo contra MinIO/S3 y resuelve las rutas contra el registro de metadatos en Postgres, sin la vuelta extra de serializar a JSON. Pensado tanto para uso interno (jobs, notebooks) como para cualquier proyecto que quiera leer datasets sin pasar por la API REST.

Instalación

pip install -e ./backend/libs/client

O como dependencia en otro proyecto (vía git, hasta que se publique en un índice):

pip install git+https://github.com/BIOS-Co/DATALAKE.git#subdirectory=backend/libs/client

Configuración

Todos los parámetros son opcionales al construir el cliente — si no se pasan, se leen de variables de entorno (así el mismo código funciona dentro de Docker, usando nombres de servicio, y afuera, usando localhost o la IP de la VM):

export STRATEGODATA_S3_ENDPOINT=http://<host>:9000
export STRATEGODATA_S3_ACCESS_KEY=admin
export STRATEGODATA_S3_SECRET_KEY=<password>
export STRATEGODATA_REGISTRY_DSN=postgresql://strategodata:<password>@<host>:5432/strategodata

from strategodata_client import StrategoDataClient

dl = StrategoDataClient()  # usa las variables de entorno de arriba

# o explícito:
dl = StrategoDataClient(
    s3_endpoint="http://localhost:9000",
    s3_access_key="admin",
    s3_secret_key="<password>",
    registry_dsn="postgresql://strategodata:<password>@localhost:5432/strategodata",
)

Uso

Leer

df = dl.read("gold.resumen_diario_por_clase")            # -> pandas.DataFrame
df = dl.read("gold.resumen_diario_por_clase", limit=100)  # solo las primeras 100 filas

tabla = dl.read_arrow("gold.resumen_diario_por_clase")     # -> pyarrow.Table, más eficiente para datasets grandes

Escribir

dl.write(df_nuevo, "gold.mi_resultado")                    # mode="append" por default
dl.write(df_nuevo, "gold.mi_resultado", mode="overwrite")
dl.write(df_nuevo, "gold.mi_resultado", partition_columns=["fecha"])  # particionado Hive-style

Si el namespace (capa) no existe todavía, se crea automáticamente al escribir — no hace falta un paso previo de "crear bucket" ni "crear tabla".

Explorar

dl.list_namespaces()                          # ['bronze', 'silver', 'gold']
dl.list_tables("gold")                        # ['resumen_diario_por_clase', ...]
dl.table_schema("gold.resumen_diario_por_clase")  # {'clase': 'large_string', ...}

Escritura y concurrencia

Un write(..., mode="overwrite") no borra y reescribe en el lugar: escribe en una carpeta nueva con nombre único y recién al final mueve el puntero del registro de metadatos a esa carpeta. Sin esto, dos escritores overwrite concurrentes sobre la misma tabla (por ejemplo, un trigger manual de Airflow que se cruza con la corrida programada) corrompen el dataset, porque ambos borrarían y escribirían en el mismo directorio a la vez. La versión anterior se borra recién después, de forma best-effort — si esa limpieza falla, o si otro escritor ya la reemplazó, queda una carpeta huérfana en MinIO (basura inofensiva), no un dataset corrupto para los lectores.

mode="append" no tiene este problema — solo agrega archivos nuevos, no borra nada.

Errores del lado del cliente

strategodata_client no atrapa excepciones — las deja subir tal cual, para que el código que lo llama decida cómo manejarlas:

Excepción Cuándo ocurre
ValueError("table_name debe tener formato 'capa.tabla'...") Se llamó a read/write/table_schema con un nombre sin punto, ej. dl.read("resumen") en vez de dl.read("gold.resumen").
ValueError("Dataset '...' no existe en el registro") Se intentó leer o pedir el esquema de una tabla que nunca se escribió.
Excepciones de psycopg2 Problema de conexión a Postgres (DSN incorrecto, base caída).
Excepciones de s3fs/pyarrow Problema de conexión a MinIO/S3, o datos corruptos en el path registrado.

Para más contexto sobre cómo estos mismos casos se traducen a códigos HTTP cuando se consume vía la API REST en vez del cliente Python, ver manejo de errores.

Diferencias con la versión anterior (Iceberg)

Este cliente reemplazó un catálogo Iceberg REST por este registro de metadatos propio en Postgres. A cambio de simplicidad operativa (sin servicio de catálogo aparte, todo corre en una VM), se pierden:

  • Transacciones ACID entre escritores concurrentes de tablas distintas (dentro de una misma tabla, ver la nota de concurrencia arriba).
  • Time travel — no hay table_history/read_as_of.
  • Evolución de esquema automática entre escrituras con columnas distintas.

Si estas garantías se vuelven necesarias más adelante, se puede reintroducir un table format (Iceberg o Delta Lake) sin cambiar la interfaz pública del cliente (read/write/list_tables).
